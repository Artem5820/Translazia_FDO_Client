# Лабораторная работа №8
## Разработка на основе структурированных промптов

### Цель работы

Изучить и применить методологию разработки на основе структурированных промптов (Structured-Prompt-Driven Development, SPDD) для управляемой генерации программного кода с помощью большой языковой модели. Освоить использование структурированных промптов как версионируемых, проверяемых и повторно используемых артефактов разработки.

Методологической основой работы является статья Martin Fowler «Structured-Prompt-Driven Development»:
https://martinfowler.com/articles/structured-prompt-driven/

### 1. Выбор задачи для разработки

В рамках лабораторной работы была выбрана задача доработки существующего модуля анализа учебных видеотрансляций из курсового проекта.

Назначение модуля:

- прием видеозаписи трансляции;
- анализ кадров с определением визуального состояния;
- разбиение видео на смысловые сегменты;
- формирование итогового результата анализа в формате JSON.

В качестве практической задачи для SPDD была выбрана доработка данного модуля по следующим направлениям:

1. сокращение избыточного объема итогового JSON;
2. перевод пользовательского вывода на русский язык;
3. добавление событийного режима;
4. добавление режима фиксации проблемы по ходу анализа;
5. уточнение правил обработки стартовой аватарки, черного экрана и сцен с доской.

### 2. Изначальные требования к разрабатываемому модулю

До начала доработки были сформулированы следующие требования.

Функциональные требования:

1. модуль должен принимать на вход видеозапись;
2. модуль должен определять основные состояния трансляции;
3. модуль должен формировать результат в формате JSON;
4. модуль должен поддерживать компактный режим вывода только с проблемами;
5. модуль должен поддерживать событийный режим;
6. модуль должен уметь фиксировать проблему не только в конце, но и во время анализа;
7. стартовая аватарка в начале трансляции не должна автоматически считаться ошибкой;
8. кратковременный черный экран не должен автоматически считаться технической проблемой;
9. модуль должен корректно работать на видео с уроком у доски;
10. основные правила должны быть покрыты тестовыми сценариями и модульными тестами.

Нефункциональные требования:

- вывод должен быть понятным и пригодным для интеграции во внешнюю систему;
- доработка не должна ломать существующий CLI;
- промпты должны храниться как отдельные документы;
- итоговый код должен оставаться пригодным для дальнейшего повторного использования.

### 3. Анализ требований и контекста существующей кодовой базы

Перед составлением промпта был проведен анализ существующей кодовой базы проекта.

В процессе анализа были выделены основные доменные концепции:

- `наблюдение` — состояние трансляции в конкретный момент времени;
- `сегмент` — непрерывный участок видео с одинаковой интерпретацией;
- `состояние` — тип сцены, например демонстрация экрана, преподаватель в кадре, аватарка, пустая аудитория;
- `решение` — итоговая трактовка сегмента: нормальный ход занятия, возможная проблема, техническая проблема, завершение трансляции;
- `событие` — факт появления или исчезновения проблемы.

Были проанализированы основные файлы проекта:

- [vk_video_analyzer/analyzer.py](C:/Module_video_analys/vk_video_analyzer/analyzer.py)
- [vk_video_analyzer/cli.py](C:/Module_video_analys/vk_video_analyzer/cli.py)
- [vk_video_analyzer/config.py](C:/Module_video_analys/vk_video_analyzer/config.py)
- [vk_video_analyzer/heuristics.py](C:/Module_video_analys/vk_video_analyzer/heuristics.py)
- [vk_video_analyzer/schemas.py](C:/Module_video_analys/vk_video_analyzer/schemas.py)
- [tests/test_state_rules.py](C:/Module_video_analys/tests/test_state_rules.py)

В ходе анализа были выявлены основные бизнес-правила:

1. демонстрация экрана и преподаватель в кадре являются нормальными учебными сценариями;
2. стартовая аватарка в начале трансляции может быть допустимой;
3. слишком длинная стартовая аватарка является признаком возможной проблемы;
4. финальная аватарка после длительной нормальной трансляции может означать завершение занятия;
5. кратковременный черный экран скорее является переходом, чем ошибкой;
6. длительный черный экран должен считаться технической проблемой;
7. сцены с доской без преподавателя в отдельных кадрах не должны автоматически интерпретироваться как ошибка.

Также были выявлены технические риски:

1. итоговый JSON был слишком большим;
2. часть реальных кейсов давала ложные срабатывания;
3. сцены с доской обрабатывались не всегда корректно;
4. длительные прогоны на CPU выполнялись медленно.

Стратегическое решение состояло в том, чтобы не переписывать модуль полностью, а доработать существующую архитектуру локальными изменениями, сохранив совместимость с текущим CLI и структурой проекта.

### 4. Структурированный промпт по REASONS Canvas

После анализа требований был составлен структурированный промпт по схеме REASONS Canvas:

- `Requirements` — требования к результату;
- `Entities` — сущности предметной области и кода;
- `Approach` — общий подход к реализации;
- `Structure` — точки встраивания изменений;
- `Operations` — действия, которые необходимо выполнить;
- `Norms` — инженерные правила выполнения доработки;
- `Safeguards` — ограничения и защитные условия.

В работе были использованы две версии структурированного промпта:

- [prompts/prompt_v1.md](C:/Module_video_analys/lab8_spdd/prompts/prompt_v1.md)
- [prompts/prompt_v2.md](C:/Module_video_analys/lab8_spdd/prompts/prompt_v2.md)

Первая версия была предназначена для реализации компактного русскоязычного JSON и событийного режима. Вторая версия была подготовлена после функциональной проверки и содержала уточнения по стартовой аватарке, черному экрану, live-режиму и сценариям с доской.

### 7. Функциональная проверка модуля и корректировка промпта

После первой итерации генерации была проведена функциональная проверка на тестовых и реальных видео.

В ходе проверки были обнаружены следующие проблемы:

1. результат по-прежнему был избыточным в ряде сценариев;
2. проблема недостаточно рано фиксировалась по ходу анализа;
3. стартовая аватарка иногда ошибочно определялась как проблема;
4. короткий черный экран трактовался слишком строго;
5. на видео с доской возникали ложные срабатывания на аватарку;
6. часть времени урока у доски не учитывалась как уверенное время занятия.

После этого структурированный промпт был скорректирован, и по второй версии были выполнены дополнительные изменения кода.

В результате доработки были:

- добавлены режимы `events` и `live-events`;
- введен порог допустимой стартовой аватарки;
- введен порог длительности черного экрана;
- уточнены приоритеты состояний;
- уменьшены ложные срабатывания на аватарку;
- улучшен расчет времени занятия.

Таким образом, корректировка промпта использовалась как основной механизм управляемого улучшения результата.
