# Лабораторная работа №8

## Разработка на основе структурированных промптов

### Цель работы

Изучить и применить методологию разработки на основе структурированных промптов (Structured-Prompt-Driven Development, SPDD) для управляемой генерации программного кода с помощью большой языковой модели. Научиться использовать структурированные промпты как версионируемые, проверяемые и повторно используемые артефакты разработки.

Методологической основой является статья Martin Fowler «Structured-Prompt-Driven Development»:  
https://martinfowler.com/articles/structured-prompt-driven/

### 1. Выбор задачи для разработки

В рамках лабораторной работы была выбрана задача разработки аудиомодуля SoundChecker для курсового проекта.

Модуль предназначен для анализа звуковой дорожки учебной трансляции. Общая система модерации предполагает, что клиент передает запись занятия на сервер, сервер разделяет видео и аудио, после чего аудиодорожка направляется в SoundChecker.

Границы работы:

– клиентское приложение не реализуется;

– серверная часть не реализуется;

– модуль анализа видео не реализуется;

– реализуется только анализ аудиодорожки и формирование JSON-результата.

### 2. Изначальные требования

Функциональные требования:

– принимать путь к аудио или видеофайлу;

– извлекать аудиодорожку;

– приводить звук к mono 16 кГц;

– определять наличие речи;

– определять почти полную тишину;

– определять низкую громкость;

– определять клиппинг;

– рассчитывать спектральные признаки;

– возвращать результат в JSON;

– поддерживать русский вывод JSON для демонстрации.

Нефункциональные требования:

– использовать Python;

– использовать готовую модель VAD, а не обучать модель с нуля;

– отделить CLI от ядра анализа;

– обеспечить возможность запуска из консоли;

– сохранить пригодность модуля для последующей интеграции с сервером.

### 3. Анализ требований и контекста кодовой базы

В ходе анализа были выделены основные доменные концепции:

– аудиодорожка;

– речевая активность;

– тишина;

– громкость;

– клиппинг;

– шум;

– спектральные признаки;

– проблема звука;

– итоговый статус;

– JSON-результат.

Бизнес-правила:

– если речь не обнаружена, статус должен быть `critical`;

– если аудио почти полностью состоит из тишины, статус должен быть `critical`;

– если речь есть, но громкость низкая, статус должен быть `warning`;

– если обнаружен клиппинг, гул или шум, статус должен быть `warning`;

– если проблем нет, статус должен быть `ok`;

– если есть хотя бы одна критическая проблема, итоговый статус должен быть `critical`.

Технические риски:

– входные файлы могут иметь разные форматы;

– ffmpeg может быть не найден в PATH;

– Silero VAD может быть не установлен;

– шум или музыка могут быть ошибочно приняты за полезный сигнал;

– пороги могут требовать калибровки на реальных трансляциях;

– русский JSON может вызвать проблемы при неправильной кодировке.

Стратегические решения:

– использовать ffmpeg для декодирования;

– использовать NumPy для расчетов;

– использовать Silero VAD для определения речи;

– добавить fallback без VAD;

– добавить спектральные метрики;

– выводить результат в stdout;

– локализовать ключи JSON на уровне CLI.

### 4. Структурированный промпт по REASONS Canvas

Структурированные промпты были оформлены по схеме REASONS Canvas. Все версии промптов вынесены в файл:

[prompts/prompts.md](prompts/prompts.md)

Использованные элементы REASONS Canvas:

– Requirements: требования к результату;

– Entities: сущности предметной области и кода;

– Approach: общий подход к реализации;

– Structure: структура проекта и точки изменения;

– Operations: конкретные действия, которые должна выполнить LLM;

– Norms: инженерные правила выполнения;

– Safeguards: ограничения и защитные условия.

### 5. Генерация кода с помощью LLM

Для генерации и доработки кода использовалась большая языковая модель ChatGPT.

Работа выполнялась итерационно:

1. был составлен первичный промпт для создания прототипа;

2. была добавлена VAD-модель;

3. был добавлен спектральный анализ;

4. был добавлен русский JSON-вывод;

5. были составлены тестовые сценарии;

6. после функциональной проверки был уточнен итоговый статус.

В результате были сформированы и доработаны следующие файлы проекта:

– `soundchecker/audio.py`;

– `soundchecker/analyzer.py`;

– `soundchecker/cli.py`;

– `soundchecker/spectrogram.py`;

– `requirements.txt`;

– `requirements-vad.txt`.

### 6. Генерация тестовых сценариев

На основе тех же требований были сформированы тестовые сценарии. Они вынесены в отдельный файл:

[test_scenarios.md](test_scenarios.md)

Основные проверяемые случаи:

– нормальная речь;

– почти полная тишина;

– тихая речь;

– перегруз;

– отсутствие входного файла;

– сохранение спектрограммы;

– русский JSON;

– технический английский JSON.

### 7. Функциональная проверка и корректировка

Функциональная проверка была выполнена на двух файлах:

– `тестречь.mp3`;

– `тесттишина.mp3`.

Для файла `тестречь.mp3` модуль вернул статус `ok`, пустой список проблем, долю речи `0.9215` и долю тишины `0.3251`.

Для файла `тесттишина.mp3` модуль вернул статус `critical`, так как были обнаружены проблемы `no_speech`, `mostly_silence` и `low_volume`.

После проверки было уточнено правило формирования итогового статуса: если среди проблем есть хотя бы одна критическая, общий статус должен быть `critical`.

### 9. Вывод

В ходе лабораторной работы была применена методология SPDD для разработки модуля SoundChecker. Структурированные промпты использовались как управляемые артефакты разработки: они фиксировали требования, предметные сущности, подход, структуру, операции, нормы и ограничения.

Итерационный подход позволил постепенно получить рабочий модуль: сначала был создан базовый анализатор аудио, затем добавлена модель обнаружения речи, спектральные признаки, русская локализация JSON и тестовые сценарии.

Итоговый код соответствует исходным требованиям и может использоваться как самостоятельный консольный аудиомодуль или как часть серверной системы модерации учебных трансляций.
