# Разработка модуля SoundChecker по методологии SPDD

## 1. Цель работы

Целью работы является применение методологии Structured-Prompt-Driven Development, далее SPDD, для управляемой разработки программного модуля анализа аудиодорожки учебной трансляции.

В рамках курсового проекта разрабатывается модуль SoundChecker. Модуль принимает аудио или видеофайл с аудиопотоком, анализирует наличие речи, тишину, громкость, перегруз, шумовые и спектральные признаки, после чего возвращает результат в формате JSON.

SPDD используется как способ формализовать взаимодействие с большой языковой моделью. Промпты рассматриваются не как разовые сообщения, а как артефакты разработки: их можно версионировать, проверять, уточнять и повторно применять.

## 2. Выбранная задача

Для разработки выбрана задача создания аудиомодуля для системы модерации трансляций занятий у студентов заочной формы обучения.

Общая система предполагает следующую архитектуру:

– клиент передает запись или поток занятия на сервер;

– сервер разделяет видеоряд и аудиодорожку;

– видеоряд отправляется в отдельный модуль анализа видео;

– аудиодорожка отправляется в модуль SoundChecker;

– SoundChecker возвращает JSON с результатом анализа;

– сервер агрегирует данные и передает результат клиенту или модератору.

В рамках данной работы реализуется только аудиомодуль. Клиентское приложение, сервер и видеомодуль не реализуются.

## 3. Изначальные требования к модулю

Функциональные требования:

– модуль должен принимать путь к аудио или видеофайлу;

– модуль должен извлекать аудиодорожку и приводить ее к единому формату;

– модуль должен определять наличие речи;

– модуль должен определять длительную тишину;

– модуль должен определять слишком низкую громкость;

– модуль должен определять перегруз аудиосигнала;

– модуль должен рассчитывать спектральные признаки;

– модуль должен возвращать результат в формате JSON;

– вывод JSON должен быть пригоден для последующей интеграции с сервером;

– на этапе демонстрации JSON должен выводиться с русскими названиями полей.

Нефункциональные требования:

– модуль должен быть реализован на Python;

– код должен быть разделен на логические файлы;

– модуль должен запускаться из командной строки;

– анализатор должен быть отделен от CLI, чтобы его можно было переиспользовать;

– модель обнаружения речи должна быть готовой, без обучения с нуля;

– отсутствие VAD-модели не должно полностью ломать работу модуля;

– результат должен быть интерпретируемым для модератора.

## 4. Анализ требований и контекста кодовой базы

Перед генерацией кода был определен контекст существующей системы.

Доменные концепции:

– аудиодорожка занятия;

– речевая активность преподавателя;

– тишина;

– громкость;

– клиппинг;

– шум;

– спектральная структура сигнала;

– JSON-результат анализа;

– модератор трансляции.

Бизнес-правила:

– если речь не обнаружена, результат должен считаться критическим;

– если аудио почти полностью состоит из тишины, результат должен считаться критическим;

– если речь есть, но громкость низкая, результат должен быть предупреждением;

– если есть перегруз, гул или шум, результат должен быть предупреждением;

– если проблем нет, результат должен иметь статус `ok`;

– если есть хотя бы одна критическая проблема, итоговый статус должен быть `critical`;

– если есть только некритические проблемы, итоговый статус должен быть `warning`.

Технические риски:

– разные форматы входных файлов;

– отсутствие ffmpeg в PATH;

– несовместимость Silero VAD с некоторыми версиями Python;

– ложное распознавание музыки или шума как полезного сигнала;

– слишком жесткие или слишком мягкие пороги;

– проблемы кодировки при русском JSON-выводе.

Стратегические решения:

– использовать ffmpeg для декодирования аудио;

– приводить аудио к mono 16 кГц;

– использовать Silero VAD как готовую модель обнаружения речи;

– дополнить VAD энергетическими и спектральными метриками;

– хранить пороги в отдельной конфигурации;

– выводить JSON в stdout;

– оставить CLI как первый интерфейс интеграции.

## 5. REASONS Canvas

### 5.1 Requirements

Нужно разработать Python-модуль анализа аудиодорожки учебной трансляции. Модуль должен принимать файл, извлекать звук, определять наличие речи и технические проблемы звука, после чего возвращать JSON.

### 5.2 Entities

Основные сущности:

– входной файл;

– аудиосигнал;

– частота дискретизации;

– конфигурация порогов;

– речевая активность;

– спектральные признаки;

– проблема звука;

– итоговый статус;

– JSON-результат.

### 5.3 Approach

Подход состоит из нескольких этапов:

– декодировать файл через ffmpeg;

– привести звук к mono 16 кГц;

– рассчитать RMS, peak, долю тишины и долю перегруза;

– определить речь через Silero VAD;

– рассчитать спектральные признаки через STFT;

– применить правила классификации;

– сформировать JSON.

### 5.4 Structure

Предлагаемая структура проекта:

```text
soundchecker/
  __init__.py
  __main__.py
  audio.py
  analyzer.py
  spectrogram.py
  cli.py
requirements.txt
requirements-vad.txt
README.md
```

### 5.5 Operations

Основные операции:

– `load_audio(path)` загружает и нормализует аудио;

– `analyze_audio(samples, sample_rate, config)` рассчитывает метрики и проблемы;

– `_try_silero_vad(samples, sample_rate)` определяет долю речи;

– `_spectral_metrics(samples, sample_rate)` рассчитывает спектральные признаки;

– `_overall_status(issues)` определяет итоговый статус;

– CLI печатает JSON в консоль.

### 5.6 Norms

Нормы разработки:

– код должен быть понятным и разделенным по ответственности;

– магические числа должны быть вынесены в конфигурацию;

– ошибки загрузки аудио должны возвращаться как JSON;

– сообщения для демонстрации должны быть на русском языке;

– технические коды проблем должны оставаться стабильными;

– модуль не должен зависеть от серверной части.

### 5.7 Safeguards

Меры защиты от ошибок:

– проверка существования входного файла;

– fallback для WAV при отсутствии ffmpeg;

– fallback для speech ratio при отсутствии Silero VAD;

– ограничение нижней границы dBFS;

– отдельные пороги для критических и предупредительных проблем;

– тестирование на файлах с речью и тишиной.

### 6.3 Prompt v3: спектральный анализ

```text
Роль:
Ты специалист по цифровой обработке сигналов и Python.

Контекст:

```

## 10. Вывод

В ходе работы была применена методология SPDD для разработки модуля SoundChecker. Вместо неструктурированного запроса к LLM были сформированы последовательные промпты, каждый из которых решал отдельную задачу: создание базового прототипа, добавление VAD, добавление спектрального анализа, локализация JSON и генерация тестовых сценариев.

Использование REASONS Canvas позволило явно описать требования, сущности, подход, структуру, операции, нормы и защитные меры. Это сделало процесс генерации кода более управляемым и проверяемым.

Итоговый модуль соответствует исходным требованиям: он анализирует аудиодорожку, выявляет ключевые проблемы звука и возвращает интерпретируемый JSON. Промпты можно хранить в репозитории, версионировать и использовать повторно при дальнейшей доработке проекта.
